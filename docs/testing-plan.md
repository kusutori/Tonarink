## 决策摘要

- 统一 MSTest + Microsoft.Testing.Platform，不再长期保留多套测试框架
- 六个主要测试套件分别负责 Core、共享业务、命令契约、CLI 进程、WinUI 控件和主 App 用户流程
- 优先迁移已有有效案例，再按功能矩阵补齐缺口，不为了数量重复断言
- UI 分为真实控件测试和跨进程用户操作测试，编译或源码文本检查不能替代它们
- 排版、禁用状态和键盘可达性用真实布局及交互断言验证，不以动画截图比较代替功能测试
- 快速、完整、发布三个运行档位；最终 AOT MSIX 与 CLI 分发产物必须单独验证
- 不做动画关键帧视觉比较，也不在测试过程中覆盖开发者的生产安装与数据

实施顺序：P0 可行性验证 → P1 迁移清理 → P2 Core/业务 → P3 CLI → P4 App → P5 CI/产物门禁。P2～P4 可以穿插推进，但每项完成都要有明确的运行证据。

## 1. 目标与范围

统一使用 MSTest 与 Microsoft.Testing.Platform（MTP），覆盖 Core、共享业务层、独立 CLI、主 App 集成 CLI、WinUI 控件和最终分发产物。统一框架、版本、报告、分类和运行入口，但不把不同运行环境的测试合并为一个项目。

“完整”指所有公开能力、CLI 命令、App 页面和平台功能都有明确的验证责任，并覆盖正常、失败、边界、状态转换和持久化。它不等于逐行测试、100% 覆盖率，也不意味着可以自动验证所有外部系统行为。

范围约定：

- 保留并迁移有实际行为价值的现有测试，修正过时需求
- 添加真实网络、真实进程、真实 WinUI 和真实发布产物测试
- 动画不做关键帧、像素或视觉快照比较；只在需要时验证触发、状态恢复和生命周期
- 不把源码字符串检查、编译成功或手工调试记录称为 UI 自动化测试
- 不为测试重复实现生产逻辑，不建立自制命令解析器或测试 DSL
- 本计划不授权修改发布、签名、商店提交或用户机器上的生产应用数据

## 2. 迁移前基线与主要缺口

方案讨论时仓库有 7 个 xUnit 测试项目。Core 已有真实节点、HTTP/TLS、传输可靠性和 Web 分享测试；Application 和 LocalSend 适配层已有部分业务测试；设置项目混合了纯逻辑测试和读取源码的结构检查。以下记录迁移前的问题，不表示它们在后续工作区中仍全部存在。

需要纠正的现状：

1. `ci.yml` 的 `ui` 作业只检查格式、编译主 App 和发布组件，没有执行 WinUI 界面
2. 常规 CI 没有运行设置、LocalSend 业务适配和 Blazor 结构测试；Mobile 作业被禁用
3. 设置测试通过 `Compile Include` 链接部分生产源码，并将 UI 源码作为文本检查，没有运行生产 App 的组件
4. 部分旧断言与现有需求不符，例如删除预览覆盖卡片不应改变下拉框选择的工具
5. `OfficialClientInteropTests` 只检查互通记录文档，并未操作官方客户端
6. CLI 产物已有 `Verify-CliTool.ps1` 冒烟验证，但没有覆盖全部命令及失败路径
7. 之前的 DevTools、WinApp 和 AOT 崩溃验证未固化成持续运行的回归套件
8. 尚无可用于声明整体代码覆盖率的统一报告

实施前重新清点测试发现结果、实际运行结果和 CI 范围。源码方法数量不作为运行成功的证据。

### 3.1 项目依赖与被测入口

统一 MSTest 不代表把所有测试放进主 App 项目。生产项目不引用测试项目，测试套件之间不互相引用；共用夹具放入 `Tonarink.TestSupport`，只提供隔离、等待、进程管理和诊断，不实现另一套产品业务。

| 套件 | 主要被测入口 | 依赖边界 |
| --- | --- | --- |
| Core | `LocalSendDotNet.Core` 的公共 API 和真实节点 | 不引入 CLI 或 WinUI |
| Application | `Tonarink.Application`、`Tonarink.LocalSend` | 平台服务可替换，实际业务及 Core 适配不能被替换掉 |
| CommandLine | `Tonarink.CommandLine` 的生产命令树、协议与宿主 | 可复用独立版的纯配置逻辑；实际独立进程行为归 CLI E2E |
| CLI E2E | 指定路径的独立 CLI apphost、tool 安装结果或 portable 文件 | 不用程序集内直接调用代替进程启动、退出和持久化 |
| App WinUI | 通过项目引用复用的生产 App 组件与平台实现 | 拥有真实窗口与 dispatcher；Windows 依赖不进入跨平台辅助库 |
| App E2E | 外部启动的生产 App、包身份与执行别名 | 控制器不以挂载测试页面或直接调用页面方法代替用户流程 |

这张表约束验证责任，不要求为整理目录立即重构所有项目引用。新增辅助代码先判断是否属于测试设施；若是产品能力或正常运行所需的依赖，应放回对应生产模块。

## 4. 框架、引用与分类规范

### 4.1 统一运行栈

- 测试项目使用 `MSTest.Sdk`，在 `global.json` 统一固定版本并选择 MTP runner
- WinUI 自宿主支持以 MSTest 4.5 / MTP 2.5 为目标；实施时先核对可获取且相互匹配的稳定版或预览版，禁止只照抄文档版本号
- 使用同一套 TRX、覆盖率和诊断扩展；核对扩展许可及 CI 支持，不无差别启用所有扩展
- 更新测试命令、过滤器和报告参数，不沿用不适用于 MTP 的 VSTest 调用方式
- 最终移除 xUnit、xUnit runner、旧 VSTest-only 配置及不再使用的 collector
- 迁移期间允许短暂共存，但每批有明确迁移对象，最终状态不能保留无理由的双框架
- 不全局给测试项目设置 `PublishAot`；JIT 测试控制器也可以验证真实 AOT 被测进程

版本记录：当前工作区的 `global.json` 固定 `MSTest.Sdk` 4.4.1；微软新文档描述的完整 Windows 应用支持矩阵以 4.5 / MTP 2.5 为目标，作者在博客补充说明实际以 4.5.1 发布。版本选择以实施时包源可还原结果和实际运行验证为准，本文不修改 SDK 配置。不能据此假定现用版本已支持全部打包模型，也不能只为匹配文档而引用不可还原的版本。P0 分别验证非打包控件宿主、打包身份与 CI 启动路径，再决定是否升级；全局 MTP runner 切换与残留套件迁移一并完成。[版本说明](https://devblogs.microsoft.com/dotnet/testing-uwp-and-winui-3-apps-with-mstest/)

### 4.2 引用生产实现

优先项目引用；必要时使用范围明确的 `InternalsVisibleTo`。不再靠复制、链接生产源码构造另一套行为实现，不复制 Reactor 内部测试 API。

能跨平台的业务逻辑优先复用现有 `Tonarink.Application`。只有确实被 WinUI 依赖阻碍测试的逻辑才评估抽离；不为目录整齐重建整个业务层，也不把 Windows 平台类型移入跨平台库。

先验证 WinUI 测试宿主能复用生产组件、样式、Toolkit 元数据、生成的 Lottie 类和 PRI 资源。若需要生产 UI 类库，作为经验证的独立架构调整记录，不默认通过源码链接规避问题。

Reactor 的指南提供纯逻辑、真实控件与跨进程操作的分层依据，但其测试工程和 runner 是框架自身的实现，并不是本项目必须复制的结构。本项目保留这一分层，在版本可行性验证通过后采用 MSTest 原生 WinUI 自宿主；不照搬其 xUnit 或 TAP 包装链路。DevTools 用于调试和观察真实运行，不能单独替代可重复执行、有行为断言和失败退出码的测试。[Reactor 测试指南](https://github.com/microsoft/microsoft-ui-reactor/blob/main/TESTING.md)、[MSTest WinUI 自宿主说明](https://devblogs.microsoft.com/dotnet/testing-uwp-and-winui-3-apps-with-mstest/)

文档版本也需要记录：本次核对时，Reactor 仓库 `TESTING.md` 已单列 packaged selftest，在线指南仍按 unit、selftest、App E2E 三层介绍。这里采用它们共同的行为分层，并把打包身份作为必须独立验证的部署条件；不根据上游项目数量机械增加本仓库的测试项目。实施时记录所用 Reactor 包版本与参考文档提交，避免直接使用上游 `main` 才有的 API。[Reactor 当前测试工程说明](https://github.com/microsoft/microsoft-ui-reactor/blob/main/TESTING.md)、[在线指南](https://microsoft.github.io/microsoft-ui-reactor/main/testing/)

### 4.3 分类与命名

主要层次分类使用 `Unit`、`Integration`、`UI`、`E2E`、`Distribution`，必要时另加 `Smoke`、`Packaged`、`SystemIntegration` 标记。OS、架构和 JIT/AOT 等部署信息由运行配置及报告记录，不把同一案例复制成多个测试类。

测试名说明行为、条件和结果，例如 `ValidateOverride_MissingFile_DoesNotSave`。参数化测试用于真实边界，不生成仅增加数量而没有独立价值的排列。

### 4.4 夹具与替身的实施约定

MSTest 负责案例、生命周期、断言和结果；测试辅助库负责创建隔离环境与释放资源。二者都不再包装另一套用例描述语言，也不重写产品命令解析、配置规则或状态机。

| 测试层 | 夹具应提供什么 | 不应替换什么 |
| --- | --- | --- |
| Core | 临时身份与目录、真实节点、合成文件、可控制的对端故障 | 被验证的协议、TLS、传输及文件落盘实现 |
| Application | 独立配置与历史存储、必要的平台服务替身 | 保存规则、状态转换及实际 Core 适配 |
| CommandLine | 捕获输出、可控制的运行时返回值、真实 IPC 连接 | `System.CommandLine` 命令树、协议和宿主实现 |
| CLI E2E | 指定可执行文件、独立 profile、进程与端口所有权 | 后台宿主、跨命令持久化及真实收发 |
| WinUI | 真实窗口、dispatcher、生产资源、可释放的组件挂载 | Toolkit 控件、Reactor 更新和组件事件接线 |
| App E2E | 隔离用户或 VM、生产 App 启动、UIA 定位和真实输入 | 主 App 导航、系统激活和包身份 |

异步案例返回 `Task`，不使用 `async void` 或丢弃后台任务。夹具拥有的监听器、流、进程、订阅和异步工作在清理时都有有界等待；案例失败也执行清理，清理失败不能被吞掉。共享夹具只复用无状态设施，不在案例之间复用可变业务数据。

正常分支、失败分支与资源清理分开设计断言。故障注入优先使用可控制的对端、文件系统或现有平台服务接口；仅为方便测试而增加生产分支、放宽访问权限或改变公开 API，需要单独说明必要性。

此层可以替换平台服务，但不能 mock 掉被测试的业务本身。跨平台业务与 Windows App 平台服务的覆盖分别登记，避免把前者当作后者的验证。

## 7. CLI 覆盖计划

### 7.1 命令树和命令行为

直接调用生产 `System.CommandLine` 命令树，必要时替换现有 `ICliRuntime`：

- 根命令、子命令 help/version，独立与集成模式差异
- 必填、互斥、范围、未知参数、UUID、地址、路径和空值
- 所有业务命令的正确分发、错误传播、取消、超时和退出码
- stdout/stderr 分工、文本输出、NDJSON 逐行结构、进度和最终结果
- 中英文、系统语言、命令语言与 GUI 语言不同的场景
- 默认隐藏敏感字段，仅显式请求时输出允许公开的秘密
- IPC 连接、序列化、并发请求、断连、取消及不完整请求
- help、version、解析失败及只读状态查询不意外启动后台宿主

命令矩阵覆盖现有 `status`、`devices`、`discover`、`send`、`cancel`，以及 `receive`、`server`、`settings`、`favorites`、`history`、`web`、`app` 的全部子命令。新增命令同步登记，不能只验证主流程。

### 7.2 独立 CLI 进程测试

- 首次自动启动宿主、后续调用复用、多个 profile 隔离
- `--no-start`、无宿主状态、宿主异常退出及重新连接
- 启动、停止、重启服务与退出宿主的区别，退出后端口和进程释放
- 配置、身份、收藏和历史跨命令/重启持久化
- 相对路径、空格、Unicode、标准输入文本及无效文件
- 两个隔离宿主之间发送、接收、拒绝、PIN、取消和校验失败
- Web 分享及 CLI 对浏览器请求的接受/拒绝
- 并发命令和活动传输期间的停止/重启行为

共同 CLI 契约以普通测试辅助代码复用，在独立版及主 App 集成版各执行一次；主 App 不支持独立 profile 等差异明确断言，GUI 专属命令单独覆盖。

### 7.3 分发验证

验证 Native AOT portable 解压后的执行权限、启动和业务行为，以及本次构建的 NuGet RID 包实际安装后的命令行为。明确包来源，不能用缓存或公开旧版本代替当前构建。

x64 与 ARM64 的“构建成功”和“原生运行通过”分别记录。没有对应原生 runner 时，不能把交叉编译或另一架构运行当作该产物运行通过。

## 8. WinUI 与主 App 覆盖计划

### 8.1 自宿主控件测试

`Tonarink.App.WinUI.Tests` 自身创建 WinUI 窗口并托管 MSTest，通过真实 dispatcher 执行 `[UITestMethod]`，复用生产组件和资源。不额外建立 TAP 子进程解析层。

宿主在创建窗口后发布 `DispatcherQueue`，再启动 MTP。P0 验证异步 `TestInitialize`、测试体和 `TestCleanup` 都保持 UI 线程访问；`[STATestMethod]` 只提供 STA，不能替代 WinUI dispatcher。宿主将测试返回值传播为进程退出码，并在完成后关闭窗口，避免断言失败却被 CI 判定成功。[WinUI 自宿主生命周期说明](https://devblogs.microsoft.com/dotnet/testing-uwp-and-winui-3-apps-with-mstest/)

- SettingsCard/Expander 挂载、展开、收起、项目增删和重新渲染
- 状态变化后内部控件值、选择项和 `IsEnabled` 实时更新
- 配置开关更新不重建所有内容、不重复事件、不覆盖输入草稿
- 输入中不保存，显式应用/校验成功后保存，无效路径不保存
- 空路径禁用校验、反馈成功/失败、覆盖卡片与工具选择独立
- 页面生命周期、卸载清理、订阅和事件处理器释放
- 发送列表、设备状态、接收请求、历史列表及对话框状态
- 焦点、悬停和动画状态触发；不比较动画帧的几何或视觉表现
- Windows 平台服务成功、拒绝、不可用及未打包分支

真实控件断言使用可观察的值、状态和视觉树，不只检查 Element 属性，更不读取源码文本证明界面正确。

实际输入单独标记 `SystemInput` 并串行运行：鼠标悬停、焦点进入/离开、键盘输入必须通过 OS 输入路径触发。UIA 的 Invoke/SetValue 和直接调用事件处理器不能替代这些案例。交互桌面、前台窗口或输入通道不可用时，记录环境失败，不把案例改成回调调用后宣称输入验证通过。

非打包模式用于快速回归，身份相关测试使用打包配置运行；共用案例而不是复制两套。测试宿主的 MSIX 身份与最终 App 不同，因此不能替代下一层。

### 8.2 主 App 用户流程

外部 MSTest 控制器通过 WinApp UI Automation 驱动生产主 App，优先稳定的 AutomationId，避免坐标和本地化文案成为主要定位方式：

- 所有页面能进入，导航往返、滚动位置、选择和草稿正确保留
- 设置主题、语言、托盘、通知、接收、网络与实验性功能
- 展开内容动态更新、输入应用/重启、路径校验、增删覆盖配置
- 文件/文件夹/文本选择，设备选择，发送、取消、接收与历史记录
- Web 分享、收藏、设备详情和网络接口页面
- 托盘隐藏/恢复、面板与主窗口单击行为
- 通知动作、分享激活、Jump List、Explorer 命令及执行别名
- 集成 CLI 修改状态后 GUI 同步更新，GUI 更改后 CLI 查询一致
- GUI 已开启/未开启时 CLI 复用应用，避免重复实例与配置分叉

文件选择等外部系统 UI 不应让每个传输案例重复操作；保留入口自动化案例，其余通过现有公开入口准备数据。确实无法稳定自动化的 OS/设备交互列入人工清单，不宣称被模拟平台验证。

### 8.3 最终包验证

使用待发布的实际产物验证 JIT/AOT、portable/MSIX 的关键启动路径，AOT MSIX 为必需门禁：安装、激活、打开设置、展开全部配置组、核心发送/接收、集成 CLI、正常退出。

Store 身份、GitHub MSIX、Widgets 变体涉及不同功能时，分别添加有针对性的冒烟案例。真实 Store 身份包只能在隔离用户/可销毁 Windows 环境中验证，不能覆盖开发者正在使用的商店安装版。

测试产物与发布产物记录相同哈希；不可重新构建另一份“测试包”冒充对发布产物的验证。若 unsigned Store 产物必须临时签名才能侧载，单独记录源包与签名派生包哈希、签名步骤和负载一致性；派生包不上传 Store，不声称已经验证微软商店签名后的安装路径。

### 8.4 优先固化的已有回归

| 已发生的问题 | 必需观察结果 | 验证层 |
| --- | --- | --- |
| 设置页在两个实例间交替 | 至少连续三次导航往返，始终保留同一页的滚动位置和草稿 | 生产 App E2E |
| Expander 内容重载或状态不更新 | 修改关联设置、调整窗口后，内部值与禁用状态即时同步；无需切页且不丢失草稿 | WinUI 控件 + App E2E |
| 预览路径每次输入或失焦即保存 | 编辑和失焦均不写入配置；仅有效路径校验成功后保存，空值禁用、失败不保存 | 业务 + WinUI 控件 |
| Expander 内动画按钮未响应 | 悬停、焦点和点击到达生产组件，卸载后不遗留订阅；不比较图像帧 | WinUI 控件 + 输入 E2E |
| AOT MSIX 打开设置崩溃 | 待发布包安装后打开设置并展开全部配置组，进程存活、操作有效、日志无未处理异常 | 最终包 E2E |

回归案例必须断言问题本身，例如页面状态保留或保存次数，而不是仅断言页面存在。对曾经出现的时序问题，记录触发步骤与等待条件，不能靠增加固定延时或多次重试掩盖。

### 8.5 排版、可访问性与真实输入的边界

之前的按钮内边距、图标画布和裁剪问题说明：仅验证外层 Button 的尺寸或事件回调不足以证明交互正确。本计划保留少量针对已知故障的布局检查，但不建立全界面像素快照或动画关键帧比较体系。

| 检查对象 | 自动化方式 | 验收结果与限制 |
| --- | --- | --- |
| 预览工具的添加按钮与下拉框 | 挂载生产组件，等待实际布局完成，读取控件在同一祖先坐标系中的边界 | 垂直中心对齐，ComboBox 保持正常控件高度；不只断言声明的 Width/Height |
| 校验和删除按钮的内容 | 同时观察按钮、内容容器及图标宿主的实际边界 | 内容居中且不被容器裁剪，命中区域完整；宿主尺寸不能证明动画内部矢量图形对齐，该部分保留人工视觉检查 |
| 设置页宽度和文本变化 | 代表性窄窗口、常规窗口及中英文运行，观察实际布局与滚动范围 | 输入框不会挤走操作按钮，标题不被压成逐字换行，必要内容可通过滚动到达；容差采用逻辑像素，避免绑定特定机器的截图 |
| 图标按钮可访问性 | 检查生产控件的 AutomationId、AutomationName、可用状态和自动化模式 | 辅助技术能识别操作，禁用状态与业务一致；测试替身中的属性不代替生产控件结果 |
| 键盘和焦点流程 | 通过 OS 输入执行 Tab、Shift+Tab、Enter/Space 和文本输入 | 焦点顺序合理、可执行操作可达，输入不意外保存；真实输入环境要求与第 8.1 节一致 |
| 悬停、焦点动画触发 | 真实输入触发，观察播放状态或现有组件的生命周期状态 | 证明输入到达组件、触发及恢复有效，不断言每帧形状、颜色或运动轨迹 |

这些检查只保护用户可操作性和曾发生的缺陷，不固定所有 Padding、字体或子节点顺序。窗口尺寸和 DPI 的代表性组合在 P0 核对可用环境后登记；未实际运行的组合不能计为通过。截图作为失败诊断或人工复核附件，不作为排版检查已通过的唯一证据。

优先使用框架及 WinUI 提供的观察能力。若必须暴露状态，采用范围明确的内部接口；不为测试添加“跳过动画”“直接调用事件”等产品分支。DevTools 和 `mur` 可协助发现实际布局与输入问题，稳定案例仍由 MSTest 负责断言、清理和失败结果。

| 设置导航 | 返回原页面状态 | 反复切换 | 滚动位置与草稿 | 生产 App 往返操作 | 待审计 |
| 执行别名 | 调用集成命令 | 无效命令、不支持选项 | 复用 GUI 设置 | 打包身份下调用别名 | 待审计 |

实际矩阵填写测试标识、运行环境、证据和人工限制。只有源码存在、编译成功或调试过，不算自动化完成。

每个行为集合使用以下用例编写约定，不额外创建测试 DSL：

1. **前置状态**：所用生产入口、隔离数据、服务/页面状态，以及必要的 OS 和包身份
2. **操作与等待**：触发真实行为，用事件或有界条件等待完成；取消案例明确区分等待接受和实际上传阶段
3. **业务结果**：同时断言返回值、可观察状态和最终内容；错误案例不能只断言“没有崩溃”
4. **副作用与清理**：检查配置、历史、临时文件、订阅、端口及自有进程；失败后验证同一实例仍可继续使用
5. **证明边界**：说明本案例使用了哪些替身、没有验证哪些平台行为，以及报告和产物身份

同一业务规则优先在最低有效层完整覆盖，上层验证接线和代表性用户流程，不把全部边界组合逐层复制。例如“无效预览路径不保存”由业务测试覆盖保存规则、WinUI 测试覆盖禁用与反馈、App E2E 覆盖真实输入与配置结果。

### 9.1 跨层用例如何分工

下面用现有功能说明实施时的分工。这是待落实的设计，不是新增的通过记录；具体已有案例与缺口以覆盖矩阵为准。

| 功能链路 | 底层完整行为验证 | WinUI 控件接线验证 | 生产 App / 分发验证 |
| --- | --- | --- | --- |
| 修改设备名称并重启 | 配置草稿、显式提交、保存失败、重启前后身份和名称；使用真实业务适配与 Core | 输入及失焦不保存，应用按钮随草稿变化，提交后显示正确状态 | 键盘输入、点击应用/重启，另一真实节点能读取新名称；返回设置不丢页面状态 |
| 选择预览工具并覆盖路径 | 工具选择独立于覆盖项；有效路径校验后保存，无效路径不保存，删除覆盖恢复自动检测 | ComboBox、添加、空值禁用、验证反馈和删除实时更新；不检查动画帧 | 实际编辑、校验、离页返回与重新启动后的结果一致；代表性文件能走选定工具的生产调用入口 |
| 发送、取消并恢复传输 | 真实 TLS 内容、PIN、失败和取消终态；临时文件、流、会话及历史清理 | 队列、设备选择、进度、取消按钮与完成状态正确更新 | 两个隔离进程完成收发；确认进入上传后取消，再用同一环境完成后续收发；CLI 分发载荷执行共同契约 |
| GUI 与执行别名协同 | 生产命令树的参数、输出、退出码和运行时边界；共享设置持久化规则 | GUI 对共享状态变化即时响应 | 真实打包身份下调用别名，GUI 开启/关闭两种情况都复用主 App 状态，不产生独立 CLI 宿主或第二份配置 |

上层只重复关键主流程与曾发生的接线故障，不重复底层的全部数据排列。需要 OS 集成、第三方程序或打包身份的步骤必须在对应环境验证；替换平台服务只能证明内部处理规则，不能登记为真实系统集成通过。

每个功能由覆盖矩阵关联到必要的各层案例。实施完成的判断是该链路的必需观察结果均有证据，而不是每层都存在一个同名测试类。

记录代码/分支覆盖率基线后再制定按模块的合理门槛，优先业务分支和失败清理路径，不用总体百分比掩盖 UI、AOT 或包身份缺口。外部原生进程没有托管覆盖率数据时，使用行为矩阵和产物验证证据，不虚构覆盖率。

### 9.2 从生产入口清点覆盖对象

“完整覆盖”先从产品入口建立清单，再对应案例；不能反过来用已有测试类推导产品只有这些功能。首轮清点使用以下来源，之后新增入口同步更新覆盖矩阵：

| 范围 | 清点依据 | 每项最少登记什么 |
| --- | --- | --- |
| Core | 公共 API、配置选项、协议入口与传输生命周期 | 正常结果、失败/取消、状态变化和资源清理责任；API 基线仅证明签名，不代替行为 |
| 共享业务 | `Tonarink.Application`、`Tonarink.LocalSend` 的状态操作与持久化入口 | 内存与落盘结果、重载、并发更新及平台边界 |
| CLI | `CliCommandLine` 的实际命令树、全局选项和运行模式 | 每个叶命令的合法输入、业务失败、输出/退出码、独立/集成差异；解析和转发分别登记 |
| App 页面 | `Pages` 下的 Send、Receive、History、Settings、DeviceDetails、NetworkInterfaces、WebShare 及实际导航入口 | 首次进入、数据更新、操作失败、离页返回和卸载；并非每项都需要重复完整 E2E |
| Windows 集成 | `Services` 下的托盘、通知、启动、分享、Jump List、Explorer 与执行别名入口 | 打包/未打包、启用/禁用、权限拒绝和实际 OS 操作；替身结果与系统结果分开 |
| 分发 | CLI RID tool/portable 与 App 实际构建变体 | OS、架构、版本、身份、哈希、安装/激活方式和执行结果 |

矩阵的每行关联生产入口、用例标识、所属套件、证明边界及结果报告。状态区分“待设计”“已编写未运行”“部分验证”“已验收”；环境不足单独注明原因，不把已编写当作已验收，也不因缺少环境删除责任。

定期核对命令树、页面和平台入口与矩阵是否一致。这个清点可以辅助发现遗漏，但不重新引入读取源码字符串来证明行为的测试。执行数量门槛用于发现漏跑；完成标准始终是必需行为及部署条件是否有证据。

## 10. 环境隔离、并行与可靠性

- 每个案例使用独立临时目录、身份、profile、接收目录和业务数据
- 网络测试避免生产默认端口；端口预选与实际绑定之间的竞争应可诊断并处理
- 用条件等待、状态事件和有上限的轮询，不依赖固定长时间 sleep
- 纯逻辑可并行；真实输入的 UI 测试串行，进程全局状态或 OS 集成案例显式隔离
- 文化设置、Console、环境变量、剪贴板、通知、托盘和包注册恢复原状态
- App 集成版不假定支持独立 CLI 的 `--profile`；优先隔离 OS 用户/测试 VM，而不是为测试更改产品行为
- 清理只针对本次拥有的进程、文件和包注册，不能宽泛按进程名终止用户应用
- 测试失败也必须清理；需要保留诊断的数据先归档
- 必需环境不可用应使对应 CI 作业失败；选做系统测试只能以明确原因报告未执行，不计为通过
- 不无条件重试到绿色。网络下载可有限重试；案例重跑保留第一次失败，单独统计不稳定性
- UI/产物案例先检查实际可执行文件、版本、身份和架构，防止测到旧进程或旧安装

## 11. CI 与发布门禁

三个档位是目标执行契约，不表示当前入口已全部实现：

| 档位 | 主要内容 | 产物与环境要求 |
| --- | --- | --- |
| 快速 | 单元、命令契约、可隔离的网络/CLI 冒烟、Windows 控件及关键导航/设置回归 | 当前源码构建；按套件分配跨平台 runner 和 Windows 交互 runner |
| 完整 | 快速档加全部业务、CLI 进程、App 用户流程、并发故障和可用的系统集成 | 隔离数据与桌面环境；未执行平台项明确列出 |
| 发布 | 已完成的完整回归，加本次发布的各 RID CLI、App AOT MSIX 和必要部署变体验证 | 消费待发布产物并记录哈希；必需门禁缺环境或失败均不得放行 |

快速档不能通过删减必需套件或静默跳过 UI 来获得绿色结果；若运行时间较长，可以拆成并行作业，但仍需分别汇总并验收。完整档也不能把仅构建、人工观察或未运行的平台项目算为通过。

### 11.1 每次提交与 PR

- Windows/Linux/macOS 执行跨平台逻辑和可隔离的网络集成测试
- 执行独立 CLI 的关键进程测试
- Windows 执行真实控件测试及关键 App E2E：启动、导航、设置更新、显式保存
- 格式检查与测试结果分开呈现，避免只看到格式失败而无法判断测试是否运行

### 11.2 完整回归

- 执行全部 CLI 命令和 App 用户流程
- 执行并发、故障、清理与平台集成案例
- 对重型或特定环境案例使用手动/定期任务，明确它们不在每次 PR 的快速范围内
- Windows 10、Windows 11 与 ARM64 的运行覆盖随原生 runner 可用性登记；未具备环境的项目保持明确缺口

### 11.3 发布前

- 构建产物后，产物验证作业消费这些产物，不独立重建
- 原生运行验证各 RID CLI 工具/portable；Windows 验证 App 的必要部署变体
- AOT MSIX 打开设置和展开全部配置组为必需门禁
- 必需门禁失败时不发布对应产物、不提交分发清单；Store 自动构建不等于自动提交商店审核
- 保存版本、提交 SHA、文件哈希、被测路径、OS/架构、案例结果和诊断附件
- 每个测试作业设超时，并核对发现与执行数量，零测试或异常缺失不能报告成功

普通 hosted Windows runner 是否提供可靠交互桌面必须先验证；不满足时使用专用交互式 runner，不跳过 UI 后保留绿色门禁。

## 12. 诊断与执行入口

统一结果写入 `artifacts/test-results/<run>/<suite>/`，至少包含 TRX 和执行摘要；失败时增加 stdout/stderr、App 日志、UIA 树、截图，按需要保存 crash/hang dump。截图仅用于定位，不建立动画视觉基线。

日志不得暴露生产 PIN、认证信息或用户真实路径/文件；测试使用合成数据，归档前检查敏感内容。

提供薄的测试调度入口，支持选择 Suite、快速/完整/发布档位以及现成 Artifact 路径。入口只负责构建、运行、传递配置和汇总退出码；断言在 MSTest 中，不在 PowerShell 中另写一套测试框架。

提供跨平台测试 solution/filter 与 Windows 测试入口，避免 Linux/macOS 为运行 Core 被迫还原 WinUI/MAUI。具体 MTP 命令在 P0 实测后写入开发文档，不提前承诺未经验证的参数组合。

### 当前入口与目标档位的衔接

当前 `tools/Invoke-Tests.ps1` 已有套件选择与指定载荷参数，但尚未提供快速、完整、发布档位参数。后续在现有入口上补齐档位映射，不另建并行的测试调度器；下面是静态核对后的入口约定，不是本次运行记录。

| 验证对象 | 当前入口 | 实施时必须补齐或确认的前置条件 |
| --- | --- | --- |
| 跨平台逻辑及命令 | `-Suite Core,Application,CommandLine` | 当前源码构建、统一结果目录及各 OS 实际报告 |
| WinUI 控件 | `-Suite WinUI` | Windows、生产资源与真实 dispatcher；不包含真实输入分类 |
| OS 输入 | `-Suite WindowsInput` | 交互桌面、目标前台窗口；不能用直接调用事件替代 |
| 独立 CLI | `-Suite Cli -CliExecutable <当前构建文件>` | 隔离 profile；JIT 与 Native AOT 载荷分别登记 |
| 原生 CLI 分发 | `tools/Verify-CliTool.ps1` | 当前版本和 RID 的本地产物、实际安装或解压、原生运行证据 |
| 主 App E2E | `-Suite AppE2E -AppLayout <当前布局> -AppExpectedSha256 <哈希>` | 当前入口面向 Sandbox 开发布局；最终 MSIX 安装验证仍需单独落实 |

常规跨平台执行的现有入口示例：

```powershell
./tools/Invoke-Tests.ps1 -Suite Core,Application,CommandLine `
    -Configuration Release -ResultsDirectory artifacts/test-results/local-logic
```

结果目录按每次执行独立命名，不能覆盖首次失败证据。`-NoBuild` 仅在对应测试宿主及被测载荷已由当前源码构建、身份已核对时使用，不作为日常默认值。完整档位必须同时汇总逻辑、控件、进程与用户流程；发布档位消费构建阶段的同一份产物，不把重新编译的文件当成待发布包。

### 12.1 先验证测试链路本身

使用独立、受控的故障夹具审计真实运行链路，至少覆盖成功、断言失败、测试宿主崩溃、协作取消、不响应取消、零案例和全部跳过。故障夹具不作为产品功能覆盖，也不能让它的预期失败混入正常套件统计。

每项审计同时核对退出码、实际执行数量、报告完整性及资源释放。报告缺失、管道断开和控制器异常必须保留原始诊断，不能根据部分成功输出推定整个运行成功。

超时采用三层约束：案例内有界等待、测试平台取消、外层控制器硬限时。取消令牌不等于强制终止；不响应取消的测试也必须在限定时间内结束本次自有进程树。CI 作业超时是最后保护，不能代替本地入口的硬限时和清理。打包启动的应用与控制器可能不是同一个进程，应验证实际宿主身份，不能只等待最初启动的进程退出。

## 13. 分阶段实施

### 单批交付与停止条件

实施不按“每次新增多少测试”推进，而按一个实际行为集合交付。每批包含：

- 覆盖矩阵中的具体缺口与所属验证层，例如“预览覆盖路径校验并保存”，而不是泛称“设置测试”
- 生产入口、案例标识、正常与失败断言，以及该案例不能证明的范围
- 实际运行环境、被测源码或产物身份、报告路径与第一次失败记录
- 对应缺口的更新；只有整个阶段的验收条件满足，才勾选阶段完成

先建立能正确报告失败的最小运行链路，再补已有故障的回归，最后按功能矩阵扩展。优先处理设置导航、Expander 状态同步、显式保存和 AOT MSIX 设置页崩溃；不把动画视觉比较放进这一批。

某个平台缺少真实运行环境时，保留该项缺口，并继续其他可独立验证的工作；不能用另一平台或测试宿主的成功代替它。若后续需要新增专用 runner、调整系统功能、安装生产身份包或修改发布权限，应先取得相应授权。

每批完成后的交付摘要使用以下格式，运行日志另放进展文档：

```text
行为集合：本批要证明的功能或既有故障
生产入口：调用哪个实际 API、命令或页面
案例与结果：标识、执行/通过/失败/未执行数量
运行身份：源码提交或工作区变更、配置、OS、架构、被测产物哈希
证据：报告、第一次失败及必要诊断的路径
证明边界：替身、未运行平台和剩余缺口
```

建议首轮交付优先级如下；依赖关系决定顺序，不预估尚未验证环境的工期：

1. 运行链路与旧案例审计，确认失败不会被吞掉
2. 设置的已知回归：导航状态、Expander 更新、草稿与显式保存
3. 最终 AOT MSIX 设置页冒烟，尽早暴露发布形态与开发形态的差异
4. Core/业务与全部 CLI 命令矩阵，包括活动传输取消、停止/重启和清理
5. 其余 App 页面、系统入口及独立/集成 CLI 一致性
6. 在真实 runner 上收敛完整回归与发布门禁

某一回归已被现有案例准确证明时复用该案例，不重复建立另一套；优先补行为断言不足或验证层不符的部分。

### 首批用例设计与交付清单

以下是实施任务，不是新的通过声明。先对照覆盖矩阵复用已有案例，再补缺失断言或验证环境。表中编号用于追踪任务，不引入测试 DSL，也不要求按编号创建测试类。

| 编号 | 行为集合与所属套件 | 关键操作 | 必须断言的结果 |
| --- | --- | --- | --- |
| T01 | 运行链路；公共辅助设施 | 运行成功、断言失败、崩溃、超时、零案例及全跳过夹具 | 退出码与实际结果一致；必需案例缺失不能报绿；只清理自有进程 |
| T02 | 草稿与显式保存；Application + WinUI | 编辑设备名称、预览覆盖路径，失焦，再应用或校验 | 编辑和失焦不写文件；合法应用只保存目标更改；无效路径不保存且有失败反馈 |
| T03 | 设置导航；App E2E | 滚动并编辑未保存草稿，至少三次离开设置再返回 | 不在两个实例间交替；滚动和草稿保留；没有重复订阅或重复保存 |
| T04 | Expander；WinUI + App E2E | 展开、修改关联开关、调整窗口、增删覆盖卡片 | 内部值及 IsEnabled 即时更新；内容不无谓卸载；草稿保留；按钮真实输入可达 |
| T05 | 活动传输生命周期；Core + CLI E2E | 确认双方已进入实际上传，再取消、停止、重启或释放节点 | 双方终态正确；部分文件清理；身份保留；端口释放；同一环境后续传输成功且内容一致 |
| T06 | CLI 命令与 IPC；CommandLine + CLI E2E | 按全部叶命令覆盖正常和业务失败，另测并发、断连及读写背压 | 正确分发、输出与退出码；取消不串请求；故障不阻塞其他客户端；宿主退出释放连接 |
| T07 | 集成 CLI；App E2E | 打包身份下调用执行别名，分别在 GUI 已启动与未启动时查询和修改 | 使用主 App 的同一份状态；不意外启动独立宿主；GUI/CLI 双向同步；不支持的选项明确失败 |
| T08 | 发布形态；Distribution + App E2E | 消费本次 AOT portable、RID tool 与 MSIX；打开设置并展开配置组 | 被测文件身份可追溯；真实包可启动及执行核心流程；必需失败阻止对应产物发布 |

每批交付同时更新案例、覆盖责任与运行证据，包含首次失败和修复后的回归结果。T03、T07、T08 缺少安全的真实运行环境时保留为未验收，不用组件宿主或解析测试替代；继续推进可独立完成的任务。

首批完成后，按照第 5～8 节覆盖其余公共能力、命令、页面与平台入口。上述八项不是完整范围的替代，也不是达到若干测试数量即可结束的标准。

### P0：基线和可行性验证

首批按以下顺序实施，先打通最小可重复链路，再扩展覆盖：

1. 清点现有项目、案例与 CI，建立旧案例迁移表及功能覆盖矩阵
2. 选择可还原的 MSTest/MTP 版本，用一个纯逻辑案例确认发现、执行、TRX 和失败传播
3. 用隔离 CLI 进程确认启动、命令执行、退出及端口释放，并完成第 12.1 节的故障审计
4. 用生产 SettingsCard/Expander 建立最小 WinUI 自宿主，确认真实 dispatcher、资源加载与动态更新
5. 在隔离 Windows 环境驱动生产 App，验证设置导航往返，再验证实际 AOT MSIX 的设置页启动

首批交付是可复用的运行基础和证据，不是所有功能的测试实现。新基础稳定后再批量迁移；已迁移部分不重复重写，但仍须通过相同的运行与报告验收。

- [ ] 审计所有现有测试、CI 范围和过时断言，建立覆盖矩阵

验收：至少一个跨平台逻辑案例、一个实际 CLI 进程案例、一个真实 WinUI 案例和一个生产 App 自动操作案例可运行；故意失败、进程崩溃、超时及零测试不会被吞为成功。可行性失败有具体阻碍和替代方案，不能跳过后直接进入发布门禁。

### 最终验收清单

以下条件用于验收整个建设目标，不以单个套件通过或某一阶段勾选替代：

- [ ] 旧案例逐项有迁移去向或删除理由；测试框架、版本与执行入口统一，没有遗留的无效源码文本检查
- [ ] Core 公共能力、全部 CLI 叶命令和 App 页面/平台入口均有覆盖责任，正常、失败、状态与清理缺口明确
- [ ] 控件测试使用生产实现和真实 dispatcher；输入测试与生产 App E2E 有独立运行证据，不冒充彼此
- [ ] 关键设置操作没有已知裁剪或不可达问题；布局断言、真实输入结果和人工视觉检查各自明确，不把宿主边界当成图标内部几何验证
- [ ] 实际受支持 OS/架构的结果可追溯；未执行项明确登记，不能用构建成功补记运行通过
- [ ] 待发布 CLI 与 AOT MSIX 的身份、哈希和结果对应；已知设置页崩溃回归及集成 CLI 属于必需验证
- [ ] 快速、完整、发布档位可重复执行；失败、崩溃、超时、零案例和必需环境缺失均正确失败，报告与清理完整

仍有必需项未验收时，整体保持进行中；人工或环境受限项目可以独立列出，但不能悄悄从既定范围移除。
